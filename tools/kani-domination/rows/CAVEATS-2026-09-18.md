several of these facts existed). Anyone quoting either row must carry these.

## 1. WALL AND MEMORY FROM THESE ROWS ARE NOT QUOTABLE

The CHC row ran on a quiet host (load 1.49 -> 3.59, zero competing engine/driver/corpus/build processes at both
ends). The BMC row did NOT: I released the host to a parallel agent the moment CHC scored, and its builds ran
throughout (load stamped 3.38 -> 10.27, and 16.75 mid-run). Individual BMC units are visibly inflated
(raw_slice/slice.rs 56.3s/4016MB, pointer-overflow/main.rs 13.1s/3003MB).
* VERDICT CLASSES are unaffected -- a class is a property of the solver's answer, not of its core count.
* WALL and PEAK-RSS from the BMC row may not be compared with the CHC row, with each other, or with Kani.
That was a deliberate trade: the parallel agent's soundness landings outrank a second lane's timings.

## 2. NOT WALL-COMPARABLE WITH LEDGER ROW 69 (nor any pre-`260c7c990` row)

Row 69 (CHC, 644/1096, 58.8%) differs from these rows in FOUR ways besides the code: route `trustc` vs
`dev-cli`, ay `10bc4b185` vs `7bb59d28b7`, jobs 3 vs 6, and macOS vs this aarch64 Linux host. `260c7c990` also
flipped the external retry OFF by default, which changes wall times and can move `unattributed_pass` rows.
Quote the two as separate measurements. What IS comparable in kind, being counts of wrongness rather than rates:
false positives 14 -> 7, error 17 -> 1, encoding_gap 31 -> 25, unknown 339 -> 319, missed_bug 0 -> 0.

## 3. THE BMC ROW MAY NOT BE RATE-COMPARED WITH LEDGER ROW 64

Row 64 is the only prior BMC row (577/1134, 51.1%). It is **scorer v2** and divides by **1134**, counting the
37 fixme units and the corpus-invalid one. Scorer v3->v5 moved `trivial_safe_pass` and `unattributed_pass` OUT
of parity. So row 64's rate was computed by a scorer that counted rows this row refuses, over a larger
denominator: 51.1% vs 47.6% is NOT a regression, and neither is it an improvement. Comparable in kind:
missed_bugs 2 -> 1, unsound_pass 5 -> 0, false_positives 74 -> 14, unsupported 221 -> 224.

## 4. THE BMC ROW CARRIES A MISSED BUG THAT IS NOW **FIXED ON MAIN** (row unchanged, and correctly so)

`expected/ptr_to_ref_cast/ptr_to_ref_cast.rs :: check_zst_deref`. Oracle FAILED, BMC SUCCESSFUL. The
file-level verdict matches (both "fail"), so only the scorer's per-harness attribution catches it; a
file-granularity oracle would have scored this parity. CHC scores the same file parity, so it is BMC-only.
Mechanism: for `zst_deref` BMC emits six obligations (misaligned x2, null x2, pointer-NULL, use-after-free)
and NO object-extent obligation, while `align_of::<Foo>() == 1` makes every alignment check vacuously true --
so nothing it asks can be false. NOT covered by the dual manifest (`grep -c ptr_to_ref_cast` = 0 of 289
entries). Three further harnesses pass only because alignment (8 -> 16) catches a SIZE bug:
`issue-3571::rust_ub_should_fail`, `ptr_to_ref_cast::check_larger_deref{,_into_ptr}`. Root cause NOT yet
established -- parameter-vs-local, use-vs-no-use, and "BMC has no extent check at all" are all REFUTED.

**FIXED 2026-09-19 in `5d0f18d47`, landed on main as `2ba77a675`.** Root cause: `resolve_ref_chain_allocation`
tested `pointee_base.contains("_deref")` against the FULLY QUALIFIED name `fn::local_N`, and the allocation's
owning function is the HARNESS -- so `check_zst_deref` read as a `_deref` alias, skipped an early return, resolved
to None, and the caller's `continue` dropped the object-extent obligation. Eight of that file's nine deref sites
died this way; `Store::<'a, LEN>::from` survived only because its name carries no `_deref`. Confirmed by the
runner: the unit scores `missed_bug -> parity`, and a full BMC lane over 815 units on the fixed bundle shows
`missed_bug 1 -> 0`, `unsound_pass 0 -> 0`.

**This row is NOT amended and must not be.** Rows 70 and 71 remain true statements about the bundle that produced
them (driver `05c02178ec88`, pre-fix). Rescoring row 71 would also be meaningless here: `rescore` re-classifies
the retained per-unit logs, which were written by the unfixed driver, so it can only restate `missed_bug=1`. If a
number is wanted for the fixed code, it needs a fresh counted row at main on a quiet host.

**Still open, and NOT closed by the fix:** `ptr_to_ref_cast` remains **0 of 291** dual-manifest entries, so the
tripwire gap that let this miss go uncounted is still open -- a discriminating dual exists but is not yet landed.
Three sibling sites share the same whole-name collision class and are untouched and unmeasured:
`statement/codegen_assign_ref_deref.rs:60`, `:401`, `statement/copy_shadow.rs:435`. And the blast-radius lane
never ran to completion (815 of 1134 units; 17 of its `crash` rows were the reviewer's own SIGKILL during
cleanup, not fix-induced).

## 5. SCORER v5, AND v6 IS **HELD**, NOT IMMINENT

Both rows are scorer v5. A v6 bump exists on branch `land/f-driver-round2` but that branch is **disqualified and
held**: it introduces `vacuity_probe_dual.rs` whose gating row
`vacuity_contradiction_after_a_definition_must_not_prove` carries only `expected` + `property` -- no `known_red`,
class, lanes or evidence -- and fails on both bundles, so landing it would add an unmarked failing gating row and
flip main's CHC dual gate pass -> fail for zero measured class changes. The bump cannot be split off: commit
`225c4b77e` carries the `SCORER_VERSION` change together with all seven qualifier sites and both modules.
So do not read "v6 inbound" into these rows' v5 label; v6 has no landing date. Neither row needs re-running when
it eventually lands:
`kani-domination rescore` re-classifies a results file from its retained per-unit logs under the current
scorer with no corpus run. Per-unit logs for both lanes are retained under
`target/kani-domination/reports/logs/trustmc-{chc,bmc}/`.

## 5a. REPRODUCIBILITY, MEASURED: a small but non-zero share of units flip class between identical runs

Measured 2026-09-19 by running the SAME bundle twice (jobs 4 and jobs 6, no code difference) and comparing the
236 units present in both:

    units with a DIFFERENT classification across two runs of one bundle: 1 of 236  (~0.4%)
      Uninit/alloc-zeroed-to-slice.rs   unsupported (30725ms)  vs  unknown (3276ms)
    wall ratio on same-class units >200ms (n=197): median 1.02x, p90 1.20x, max 1.78x

So the corpus is mostly deterministic and wall times are stable -- but ~0.4% over 1134 units is roughly 4-5
expected class flips per full-lane comparison, which is the same order as the number of real changes a targeted
fix produces. **Consequence: a single-sample class difference between two rows is a CANDIDATE, not a finding.**
Any claim that a change moved a unit's class needs n>=2 on both bundles for that unit. The soundness counters are
the exception worth confirming individually: a missed_bug is checked on its own merits, not against a distribution.

**One unit in BOTH of these rows is known to be bimodal.** `expected/loop-contract/decreases_loop_max.rs`:

    this CHC row (70): unknown / Timeout        70700ms
    this BMC row (71): unknown / UndecidedModel 70150ms
    measured elsewhere, solo and quiet, --jobs 1: **parity at ~16000ms**

It produces one ~16s `parity` or one ~70s undecided result depending on conditions, at near-identical peak RSS.
It cost these rows no parity (both scored `unknown`), so the headline numbers are unaffected -- but it means these
rows are not bit-reproducible, and re-running them will not reproduce every row exactly. The population sharing
its signature is not small: 166 BMC units exceed 30s wall (135 of them `UndecidedModel`) and 223 CHC units exceed
30s. Treat long-wall undecided rows as the least stable part of either row.

## 6. WHAT THESE ROWS DO NOT MEASURE

The owner's criterion is 100% parity "with as good or better runtime and memory". These rows measure VERDICT
PARITY only. No Kani baseline was run beside them, deliberately (see 1). The runtime/memory half requires both
engines measured back to back, same jobs, same timeout, on a quiet host.
