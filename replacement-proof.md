# trust-mc Replacement Proof Standard

This document defines what evidence is required before anyone can claim "100%
Kani replacement" for trust-mc. It is a proof standard, not a status report, and it
does not assert that the repository currently meets the bar.

## Head/Pin Guard

A replacement claim must name the exact `git rev-parse HEAD` value, exact pinned
AY revision, report `tree_fingerprint`, proof denominator, proof inventory
`row_sha256`, non-proof closure digest, and solver-binary commit attestation
used for the run. The AY revision is the pinned dependency from `Cargo.toml`;
this repository has no checked-in 100% replacement evidence packet for a
commit/pin/tree/inventory tuple until the artifacts and gates below pass on a
clean tree. Do not combine historical numerators, denominators, false-proof
status, or reports from another trust-mc commit, tree fingerprint, inventory, or AY
pin with the current dependency state.

CLI conveniences such as `--harnesses`, `--proof-summary-json`, and
`replacement_progress.py` do not change this authority model. They are review and
triage surfaces for the current workspace. The authoritative replacement proof
flow remains the inventory generator plus the hard proof gates documented here,
driven by the clean tooling under `tools/replacement-inventory/`.

## Definition

trust-mc is a 100% Kani replacement only when all of the following hold on one named
trust-mc commit, one report tree fingerprint, and one pinned 40-character `ay-chc`
revision from `Cargo.toml`:

1. The authoritative `tests/trust-mc/replacement-harness-inventory.json` manifest —
   the fresh public inventory generated by `build:inventory`
   (`tools/replacement-inventory/generate_inventory.py`) over `tests/trust-mc` and
   `tests/ay` on 2026-06-15 — is committed before the run, with the explicit
   denominator and `row_sha256` produced by that generator: mixed denominator
   **818** (`row_sha256`
   `63db917644ad68509580134eefe8cbfd2ea4848f63d27eec5dbeec08ff8b3d71`). Its **504**
   `PROOF`-expectation rows are the proof-quality subset only (`row_sha256`
   `d6645043042f739a63a74e109c03d7fea1cb6e26d978b050fe58bf414d4a5370`); the full
   818-row inventory is the whole replacement denominator, leaving **314**
   non-`PROOF` rows.

   **CURATION (fresh public corpus, generated 2026-06-15).** The 818-row corpus is
   the `#[kani::proof]` harnesses across the INCLUDED Kani verification suites:
   `tests/expected` (672 harnesses: 362 PROOF / 310 CTREX), `tests/slow` (76: 74 /
   2), `tests/std-checks` (22: 20 / 2), `tests/smack` (40: 40 / 0), and
   `tests/prusti` (8: 8 / 0). Six EXCLUDED suites are diagnostic / coverage / perf
   / CLI lanes (not single-verdict verification: compiletest does not run these as
   one verification verdict per harness): `tests/coverage`, `tests/cargo-coverage`,
   `tests/perf`, `tests/ui`, `tests/cargo-ui`, and `tests/script-based-pre`. The
   excluded suites are candidate lanes the user can opt in later; they are not part
   of the current 818 denominator.
2. Every inventory harness is run by trust-mc through the AY backend with
   `AY_SOLVER=ay`. Evidence from upstream Kani, CBMC, dirty/local AY pins,
   Rust execution, or `AY_REPORT_NON_REPLACEMENT=true` does not count.
3. Every harness has an explicit expected verdict, and every row in the
   per-harness report has `status == "PASS"`.
4. Every `PROOF` row is replacement-quality: `trusted_proof == true`,
   `known_fp != true`, `proof_qualifiers == "clean"`,
   `sound_fallback_count == 0`, `execution_state == "complete"`, and no
   demotion, translation-drop, retry, BMC-reroute, or stale metadata.
5. Expected-failure and CTREX canaries remain negative. A CTREX-to-PROOF flip is
   a blocker, not progress, unless the test expectation is intentionally changed
   with reviewer-visible justification.
6. The false-proof ledger, AY bump canaries, wrapper behavior, and public
   workflow are consistent with the same pinned run.

The committed fresh public `tests/trust-mc/replacement-harness-inventory.json` is
the full accounting denominator for Kani replacement scope: mixed denominator
**818** (`row_sha256`
`63db917644ad68509580134eefe8cbfd2ea4848f63d27eec5dbeec08ff8b3d71`). True 100%
Kani replacement requires either closing every one of the **314** non-`PROOF`
rows in that inventory or recording explicit, reviewer-visible justification in
`tests/trust-mc/non-proof-closure.json`. If any remaining row is
`UNKNOWN`, `ERROR`, `SKIP`, `XFAIL`, untriaged, or upstream-blocked without that
checked closure record, the correct statement is "not yet 100% replacement".

## Reviewer Evidence

A hostile but honest reviewer should demand:

- Raw command transcripts with exit codes, not only summaries.
- A clean source tree for all code, manifests, toolchain files, lane policy, and
  compiletest/reporting scripts. Generated files under `reports/` may change.
- Full trust-mc commit SHA, full AY pin, `command -v ay`, and proof that the report
  used solver `"ay"` with `replacement_evidence: true`.
- `ay --version` and report `.solver_binary.commit` showing a commit prefix of
  the full pinned AY revision.
- A denominator-pinned proof run using the `PROOF`-expectation rows of the
  committed `tests/trust-mc/replacement-harness-inventory.json`.
- A checked inventory manifest matching the committed
  `tests/trust-mc/replacement-harness-inventory.json`, including the denominator
  and `row_sha256` produced by `build:inventory`: mixed denominator **818**
  (`row_sha256` `63db917644ad68509580134eefe8cbfd2ea4848f63d27eec5dbeec08ff8b3d71`),
  proof subset **504** (`row_sha256`
  `d6645043042f739a63a74e109c03d7fea1cb6e26d978b050fe58bf414d4a5370`).
- A closure or explicit-justification table for every non-`PROOF` row in the
  committed inventory, checked by `tools/replacement-inventory/replacement_progress.py`
  against `tests/trust-mc/non-proof-closure.json`, with its SHA-256 digest recorded
  in the same authority tuple.
- Schema-v2 per-harness JSON loaded with current-head validation.
- Per-harness TSV for quick audit and category JSON for routing.
- A zero-fallback proof audit for all proof rows.
- Soundness-gate and AY-bump-canary logs from the same dependency state.
- A final ownership table for any non-green row. For a 100% claim that table
  must be empty except for deliberate negative canaries that pass their expected
  verdict.

Old reports, stale plans, aggregate percentages, local-only AY checkouts, or
metrics copied from another pin are not replacement evidence. Stale measurements preserved in
`README.md`, `VISION.md`, or `VERIFICATION_METRICS.md` are historical records only.
Likewise, a `--proof-summary-json` file is not replacement evidence: it only
summarizes ordinary verification results and points reviewers at this proof
flow.

## Commands

The authoritative denominator and proof-quality (`PROOF`-row) subset are read from
the committed fresh public `tests/trust-mc/replacement-harness-inventory.json`:
mixed denominator **818** (`row_sha256`
`63db917644ad68509580134eefe8cbfd2ea4848f63d27eec5dbeec08ff8b3d71`), proof subset
**504** (`row_sha256`
`d6645043042f739a63a74e109c03d7fea1cb6e26d978b050fe58bf414d4a5370`). That
committed inventory is the whole replacement denominator: every one of the **314**
non-`PROOF` rows must be closed or explicitly justified in
`tests/trust-mc/non-proof-closure.json` before claiming true 100% Kani
replacement. Replace `<trust-mc_commit>` and `<inventory_sha>` with the values
from the run and the committed inventory; the proof denominator is **504**.

For a non-authoritative progress view, use the progress reporter:

```bash
python3 tools/replacement-inventory/replacement_progress.py
python3 tools/replacement-inventory/replacement_progress.py \
  --report reports/compiletest-per-harness-latest-trust-mc.json
python3 tools/replacement-inventory/replacement_progress.py \
  --require-complete \
  --report reports/compiletest-per-harness-latest-trust-mc.json
```

This reports manifest accounting and optional report progress. Its first line is
machine-readable: `accepted_proof_quality=N/D` is the current clean proof count
accepted under authority metadata, `closed_non_proof=N/D` is the valid checked
non-proof closure count, and `accounted=N/D` is their sum. With
`--require-complete`, it exits nonzero unless the supplied report plus
`tests/trust-mc/non-proof-closure.json` establish complete replacement accounting
against the committed inventory denominator. The command prints its own replay command, expected commit/AY pin,
workspace authority context, report file and row SHA-256 digests, duplicate-key
rejection state, and the arithmetic formula for the displayed numerator. It is
the reviewer-facing progress gate, and it must be paired with the strict
authority tuple audit below before claiming 100% replacement.

If the progress report shows only non-`PROOF` accounting, for example a
`NOT_REPLACEMENT` line with the proof numerator at `0/<proof_denominator>`, that
is clean evidence only for the checked non-proof closure. It does not establish
proof-quality progress. The proof numerator advances only from current clean
schema-v2 per-harness rows that match the `PROOF` rows of the committed inventory.
The progress command can score the full report directly:

```bash
python3 tools/replacement-inventory/replacement_progress.py \
  --require-complete \
  --report reports/compiletest-per-harness-latest-trust-mc.json
```

`replacement_progress.py` prints `proof_report_problem` lines when that proof report
is missing, stale, dirty, non-schema-v2, non-replacement evidence, incomplete, or
has stale solver-binary attestation, duplicate harness keys, or proof rows that
fail the clean proof-quality checks. Long source, failure, and count summaries
are bounded; an `omitted=` or `omitted_keys=` field means the CLI printed a
stable sample and withheld additional entries.

## Must Fail Closed

Reject the replacement claim if any of these occur:

- Solver is not `ay`, the AY pin is missing/non-hex/local/dirty, the live or
  reported solver-binary commit is not a prefix of the full AY pin, or the
  report has `replacement_evidence != true`.
- The report tree fingerprint, harness count, proof inventory `row_sha256`,
  non-proof closure SHA-256, or harness identity set differs from the explicit
  authority tuple.
- A harness lacks an explicit expectation or has `status != "PASS"`.
- A proof row has fallback, demotion, translation-drop, retry, BMC-reroute,
  known-false-positive, or stale-report metadata.
- A negative canary flips to `PROOF`.
- Any command above is rerun with `--allow-stale-report`,
  `AY_REPORT_NON_REPLACEMENT=true`, `AY_REQUIRE_EXPECT=0`, or evidence from a
  different commit, tree fingerprint, inventory row digest, non-proof closure
  digest, denominator, or AY pin.
- Any unresolved row is explained only by "upstream-blocked", "triage", timeout,
  skip, or tooling failure.
